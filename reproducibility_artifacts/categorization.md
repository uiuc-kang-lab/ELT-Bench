## Error Category Definitions

### 1. Ambiguous Data Model Description:
The schema documentation provides unclear, misleading, or insufficient column descriptions, preventing accurate interpretation of the data model's intended semantics.

### 2. Semantic Interpretation Errors - Logic (Flawed SQL):
The model generates SQL that is syntactically correct but logically flawed, for example:
- Wrong aggregation method (COUNT vs SUM, wrong GROUP BY scope)
- Incorrect formula (e.g. applying discount when it shouldn't be)
- Boolean logic inversions
- Wrong window function partitioning or ordering
- Wrong value type: using 'true/false' for a data source column that actually contains 0/1

### 3. INNER vs LEFT JOIN Issues:
Wrong JOIN type causing missing or extra rows:
- INNER JOIN excludes rows when dimension tables have missing data
- FULL OUTER JOIN creates extra row combinations
- Implicit filtering through JOIN conditions

### 4. Wrong Data Source:
The model constructs queries using inappropriate source tables or columns.
#### 4.1 Missing Join:
Required JOIN operations are omitted, preventing access to necessary data sources.
#### 4.2 Wrong Table or Column:
The model references incorrect source tables, includes extraneous JOIN operations, or selects inappropriate columns from otherwise correct tables.


### 5. False Positives:
Values bteween GT and predicted semantically match but got flagged due to evaluation methodology (e.g. formattig issues, NULL mismatch, etc..):
- Same string different format between data model and data sources (and or GT)
- Timestamp precision differences or date format
- Row order differences unrelated to logic
- GT has additional rows
- Source stores decimals (0-1), GT expects percentages (0-100) or vice versa

#### 5.1 Actual Match:
Generated and ground truth results are functionally identical; discrepancy likely stems from evaluation script (stage2).

#### 5.2 Format Mismatch:
Logically correct SQL produces results in alternative valid formats, for example: the agent produces values between 0 and 1 but GT expects percentages in range 0-100.

#### 5.3 Duplicated Rows in GT:
Generated SQL is correct; mismatches arise from erroneous duplicate rows in ground truth data.

#### 5.4 NULL Mismatch:
Generated SQL is logically sound, but employs different NULL handling strategies than ground truth (e.g. COALESCE(column, 0) vs preserving NULLs) when schema documentation is silent on this specification.

#### 5.5 Row Ordering:
SQL logic is correct except for final result ordering due to absent ORDER BY clauses, typically when ordering requirements are unspecified in the schema or result from primary key generation inconsistencies.

#### 5.6 Other:
Miscellaneous issues.

### 6. Semantic Interpretation Errors - Domain Knowledge
The model lacks domain-specific understanding:
- "winnings" interpreted as race wins vs total points
- "international shipping" as different country vs non-USA
- Business terminology misunderstandings

### 7. NULL Handling Issues
The NULL semantics are not correctly used by the agent, such as not iusing a NULL FIRST logic in ordering which is assumed by the GT or some un-explicited semantics of NUL, such as NULL is treated as 'F' grade (failure) but the 'F' grade doesn't exist in the data.

### Key Generation Issues
The primary key of the resulting table has been created by the agent using a diferent method if compared to the used used by the GT, causing row ordering mismatches.

### 8. Unknown Calculation Errors
Ground truth uses calculations that cannot be derived from query/schema:
- GT values don't match any standard interpretation
- Arbitrary or undocumented business rules
- Predicted result can be very close to GT like 99.8% but not exactly 100% due to weird rows that cannot be covered by any reasonable interpretation.
